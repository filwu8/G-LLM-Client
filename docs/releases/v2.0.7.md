# G-LLM Client V2.0.7

V2.0.7 重点提升客户端速度与长时间流式回复的稳定性，并修复授权工作区后部分 NVIDIA Nemotron 模型不再回复的问题。

## 启动与交互性能

- 截图、附件、本地文件任务、工作区代理和数据压缩模块改为按需加载，减少客户端启动阶段的同步工作。
- 主窗口、快速对话和悬浮助手按窗口类型拆分加载；后台供应商目录刷新与匿名启动统计延后执行，优先完成主界面显示。
- 会话保存改为增量同步，不再在每次模型切换或保存时向所有窗口复制完整会话列表。
- 历史 Markdown 消息不再因模型切换、输入框变化或无关状态更新而重复解析。
- 流式回复按极短时间窗口合并渲染，减少高频小分片造成的界面重绘和完整消息重复计算。
- 已保存的 Token 统计直接复用，不再反复扫描长对话正文。

## 悬浮助手资源占用

- 主聊天窗口显示时不再同时创建悬浮助手渲染进程；主窗口隐藏或关闭后才加载悬浮助手。
- 悬浮助手根据状态限制为 10–30 FPS，降低空闲 CPU 与 GPU 占用。
- Apple Silicon 本地空闲采样中，主窗口 Renderer 从两个减少为一个，主进程、GPU 和 Renderer 均可回落到空闲状态。

## 工作区对话修复

- 修复第一轮普通对话正常、授权文件夹后的第二轮工作区对话长期没有回复的问题。
- 工作区代理现在兼容只用单换行分隔的 OpenAI-compatible SSE 数据，支持 Nemotron 的 `reasoning_content` 以及分片工具名称和 JSON 参数。
- 收到 `[DONE]` 后立即结束读取，不再等待上游主动关闭长连接。
- 标准双换行 SSE、普通最终文本和工作区工具调用继续保持兼容。

## 长推理与超时策略

- 移除流式回复的固定 120 秒整轮总时限，避免仍在持续输出推理内容的模型被客户端误中止。
- 连接阶段只有 120 秒内收不到响应头才判定超时；流式传输开始后，只有连续 120 秒没有收到任何新数据才判定为空闲超时。
- 模型只要持续发送答案、推理分片或 SSE 心跳，即使整轮超过数分钟也会继续接收。
- 真正的网络中断或上游长时间无数据仍会进入可恢复错误流程并提供自动重试。

## 更新方式

- Windows V2.0.6 用户可由客户端自动下载并安装 V2.0.7。
- Apple Silicon Mac（M1/M2/M3/M4 等）：下载 `G-LLM-Client-Setup-2.0.7-arm64.dmg`。
- Intel Mac：下载 `G-LLM-Client-Setup-2.0.7-x64.dmg`。
- Linux：可选择 `x86_64.AppImage` 或 `amd64.deb`。
- 本版本继续采用无证书发布；Windows/macOS 可能显示未知发布者或安全警告，macOS 与 Linux 仍需手动更新。

## English Summary

V2.0.7 improves startup, model switching, long-conversation rendering, and streaming performance. Heavy main-process features and window-specific renderers now load on demand, conversation saves use small IPC deltas, immutable Markdown messages avoid unnecessary reparsing, streaming fragments are rendered in batches, and the floating mascot no longer keeps a second renderer active while the main window is visible.

This release fixes workspace conversations that could stop responding after a folder was authorized. The workspace agent now accepts OpenAI-compatible SSE records separated by a single newline, preserves Nemotron reasoning streams, aggregates fragmented tool calls, and returns immediately when `[DONE]` arrives even if the provider keeps the HTTP connection open.

Streaming requests no longer have a fixed 120-second total lifetime. The client now applies a 120-second response-header timeout followed by a per-chunk 120-second idle timeout. Long reasoning responses remain connected as long as the provider continues sending content, reasoning deltas, or heartbeats. Genuine inactive connections still enter the recoverable retry flow.

Windows V2.0.6 clients can install this release through the in-app updater. macOS and Linux remain manual downloads under the current certificate-free distribution model.
