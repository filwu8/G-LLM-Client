# G-LLM Client 2.0.33 Windows update

Application version `2.0.33`, Windows x64 MSIX `2.0.33.0`. Store identity, publisher, application ID, `gllm` protocol and storage paths are unchanged.

**简体中文**

- 工作区 Agent 新增 `delete_file`：可以删除单个文件，删除会移入系统回收站而不是永久擦除，因此可从回收站还原。目录、符号链接、工作区外的路径以及 `.env`、`.git`、`.ssh` 一类受保护位置一律拒绝，删除前仍逐次确认。
- 审批弹窗新增「总是允许」：选择后把这次批准保存成一条持久规则，同一文件夹内同类操作不再逐次询问。保存的规则只对当前文件夹生效；脚本执行、Git 写操作和桌面控制不提供该选项。规则文件是可读的 JSON，可以手工编辑，手写的禁止规则优先于任何已保存的授权。
- 修复：拒绝一次命令后，同一任务内后续每一条命令都被重新询问，包括只读的 `ls`。拒绝记录现在按具体命令区分，一次拒绝只影响那一条命令。
- 审批策略改为两个独立维度：操作实际受到的沙箱约束，以及批准方式。完全访问不等于没有沙箱——没有隔离的操作在任何模式下都需要明确批准，保存的「总是允许」规则也不能放开它。
- 委派给 Harness 引擎的任务现在按代码执行对待，会弹窗确认；此前三种模式都不询问。
- Agent 不能再读取或改写客户端自己的审批配置文件，这类调用会被直接拒绝。
- 文档与 CI：两个从未被 CI 执行的测试登记进测试清单，并新增检查，防止将来再出现「写了测试但没登记、于是从不执行」的情况。

**English**

- The workspace agent gains `delete_file`: it removes a single file by moving it to the system recycle bin rather than erasing it, so the file can be restored. Directories, symbolic links, paths outside the workspace and protected locations such as `.env`, `.git` and `.ssh` are refused, and each deletion is still confirmed.
- The approval dialog gains an "Always allow" answer that saves the approval as a durable rule, so similar operations in the same folder stop asking. A saved rule applies only to that folder; script execution, Git writes and desktop control never offer the option. Rules are a readable JSON file that can be edited by hand, and a hand-written deny outranks any saved grant.
- Fixes re-prompting after a refusal: denying one command used to make every later command in the same task ask again, including a read-only `ls`. Refusals are now keyed by the specific command, so one refusal affects only that command.
- Approval is now driven by two independent dimensions: the sandbox confinement an operation actually has, and how it is approved. Full access does not mean "no sandbox" — an unconfined operation needs an explicit approval in every mode, and a saved "always allow" rule cannot lift that requirement.
- Tasks delegated to the Harness engine are now treated as code execution and require approval; previously none of the three modes asked.
- The agent can no longer read or rewrite the client's own approval configuration files; such calls are refused outright.
- Documentation and CI: two tests that CI had never executed are now registered in the test list, and a new check prevents the same silent drift — a written test that is never run — from recurring.

### Known limitation in this build

The About panel renders `V<version>(<build code>)`, and in 2.0.33 that code is the moment the app started, not
the moment it was built: `getAppBuildCode()` reads `statSync(__filename).mtime`, which Electron answers with the
current clock for a path inside `app.asar`. The defect is fixed on `main` (commit `107e16a`) and will ship in
2.0.34; it could not be included here because the package was already in certification.
Treat that parenthesised number as a launch timestamp. To identify a build, compare the SHA-256 of the
installed `resources/app.asar` against `release/*/release-status.json`.
