# G-LLM 助手平台架构

G-LLM 的助手运行目标是形成“理解目标 → 规划步骤 → 调用工具或其他助手 → 验证 → 交付”的闭环，并把运行反馈沉淀为可复用的 Skill。

## 助手 Manifest

每个助手包含名称、职责说明、状态（草稿、启用、暂停）、配置来源、配置版本、绑定的 Skill、绑定的工作区工具，以及允许调用的其他助手。旧版助手数据在加载时自动补齐默认状态与本地配置来源。

草稿和暂停状态的助手不能执行任务。导入的助手模板默认是草稿，需要维护者检查后手动启用。

## 工作区能力

Skill 和工具归属于工作区，可以被同一工作区内多个助手绑定和复用。启用的 Skill 会加入普通对话和工作区 Agent 的系统上下文。已绑定且启用的 HTTP 函数工具会进入工作区 Agent 的 tools 列表；函数工具使用 JSON POST 调用。MCP 和插件类型目前保存为连接器配置，运行适配器可沿同一工具注册接口继续扩展。

## 运行计划与验证

工作区任务持久化目标、执行阶段、步骤状态和验证结论。标准阶段为：

1. 理解目标与约束；
2. 检查工作区与相关资料；
3. 调用工具并完成任务；
4. 验证结果与产物；
5. 整理并交付结果。

计划和工具活动会显示在主窗口及快速对话消息中，历史消息保留最终计划和验证结论。

## 助手协作边界

只有助手 Manifest 中显式授权的调用关系才能执行。单次任务最多调用其他助手 4 次、最多 2 层，且调用路径中不得重复出现同一助手。子助手只收到边界明确的子任务和自己的系统规则，不会自动继承整个工作区或父会话内容。

## Skill 演进与评测

每次修改 Skill 规则都会生成新补丁版本并保留旧版本。运行中发现的偏差可保存为包含输入、验收关键词和实际输出的评测案例。回归检查会留下通过数、失败数及缺失验收项。回滚不会覆盖历史，而是根据旧规则生成一个新的版本。

## 模板共享

助手模板使用 `.gllm-assistant.json` 文件，包含助手及其绑定的 Skill 和工具声明。导入时会重新生成所有 ID、清除助手协作关系，并将助手设为草稿。工具地址不会被导出，导入工具默认停用，避免本地命令、内网地址或服务入口意外泄露。
